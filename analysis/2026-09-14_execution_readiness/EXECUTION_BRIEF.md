## 3. 새틀라이트(15%) — 구현 격차 발견: 페이지가 보여주는 것과 백테스트가 검증한 것이 다른 종목이다

이번 실행에서 가장 중요한 발견이다. 챔피언 엔진에는 새틀라이트를 계산하는 **서로 다른 두 함수**가
있다:

| | `compute_satellite_recommendation_point_in_time()` (백테스트가 검증한 방법) | `compute_satellite_recommendation()` (앱 페이지의 리밸런싱 diff가 실제로 쓰는 방법) |
|---|---|---|
| 방법론 | 반기(1월/7월) point-in-time 40종목 풀에서 돈치안 브레이크아웃 활성 + 12개월 모멘텀 상위 3개, 정적 보유 | S&P500 전체를 매번 스캔, 3개월 모멘텀 상위 5개 |
| 오늘 선정 종목 | **CAT, GEV, JNJ** (5%씩) | **CRWD, TRV, BBY, META, T** (3%씩) |
| 두 방법의 겹침 | **0종목 — 완전히 다른 종목 집합** | |
| final_config가 실제로 채택/백테스트한 것 | 이쪽 | 아님 |

**결론: 오늘 실제로 사야 할 새틀라이트 종목은 CAT/GEV/JNJ다 (point-in-time 방법).** CRWD/TRV/BBY/
META/T 조합은 이 프로젝트의 백테스트 성과와 아무 관계가 없는, 단순 참고용 근사 스캔의 결과다.

- **왜 이게 문제인가**: `app/pages/11_챔피언_전략.py`의 "5. 내 포트폴리오와 비교" 섹션(실제
  매수/매도 diff를 보여주는 곳, 555번째 줄 부근)은 `compute_satellite_recommendation()`(오른쪽
  컬럼, naive 스캔)의 결과를 `compute_rebalance_diff()`에 넘긴다 — `compute_satellite_recommendation_
  point_in_time()`(왼쪽 컬럼, 백테스트와 동일 방법)의 결과는 그 diff 계산에 전혀 연결돼 있지 않다.
  사용자가 그 페이지의 "사고팔아야 할 것" 표를 그대로 따라가면, 검증된 적 없는 종목을 매매하게 된다.
- **CAT/GEV가 리밸런싱 이후 각각 -17.43%/-15.61% 하락한 것은 버그가 아니라 설계다**: 이 연구
  프로그램은 "반기 중간에 트레일링스탑으로 조기 청산하는 것보다 정적으로 다음 리밸런싱까지 그냥
  들고 가는 게 기댓값 기준으로 더 낫다"는 결론을 냈다(H33/H35 감사 완료, `final_config.satellite.
  exit_mechanism` 원문: "정적 반기 리밸런싱 보유가 기댓값 기준 최선"). 그러니 지금 CAT/GEV를
  손절해야 하는지 궁금하다면 답은 "이 시스템의 설계상 아니다" — 다음 리밸런싱(2027-01, 약
  79거래일 후)까지 그대로 보유하는 것이 채택된 방법론이다. 다만 이 결론의 확신도는 "약함"이니
  (동적 방어가 방향은 있지만 통계적으로 확정 안 됨) 개인적으로 손절 규칙을 쓰고 싶다면 그것도
  근거 없는 선택은 아니다 — 이건 엔진이 자동으로 결정할 일이 아니라 사람이 판단할 영역이다.
- 3종목 모두 새틀라이트 15%를 다 배정(미배정 현금 0%) — `n_active_trend`(직전 리밸런싱 시점
  point-in-time 40종목 풀 중 활성 추세 종목 수) = 23개, top3만 선정.

## 4. 실제 보유 종목 대비 매수/매도 diff — 이번 실행에서는 계산 불가(운영상 제약, 전략 문제 아님)

`core.portfolio.get_portfolio_pnl()`/`get_cash_balance()`를 그대로 호출했지만 둘 다
`OperationalError: no such table`로 실패했다. 이 실행은 **격리된 git worktree** 안에서 돌았고, 그
worktree의 `data/quant.db`가 0바이트(테이블 자체가 생성된 적 없음)이기 때문이다 — 사용자의 실제
Codespace/서버 환경(포트폴리오 관리 페이지에 실제 보유 종목을 입력해온 곳)의 DB와는 다른, 이번
실행만의 빈 사본이다.

**그래서 이 브리핑은 "매수 N주 / 매도 N주" 같은 구체적 액션이 아니라 위 1~3절의 "목표 비중(%)"까지만
제공한다** — 사용자가 실제 보유 비중을 직접 알고 있다면(또는 `8_포트폴리오_관리` 페이지에서 확인),
위 목표비중표와 직접 비교해서 스스로 매수/매도 방향을 판단할 수 있다. 정상 환경(메인 체크아웃,
실제 데이터가 있는 곳)에서 `python3 analysis/2026-09-14_execution_readiness/compute_execution_brief.py`
또는 `app/pages/11_챔피언_전략.py`(point-in-time 탭 기준으로 3절의 구현 격차 수정 후)를 그대로
돌리면 실제 diff(달러 금액 포함)가 정상적으로 나온다. 자세한 내용은 5절 구현 격차 #2 참고.

## 5. 구현 격차 (스펙만 제시 — core/app 코드는 직접 고치지 않음)

### 격차 #1 (중요도: 중) — 리밸런싱 diff가 검증되지 않은 새틀라이트 방법을 쓴다

- **현상**: `app/pages/11_챔피언_전략.py` L555 `compute_rebalance_diff(core_result,
  satellite_result=satellite_result, holdings_pnl=holdings_pnl)`에서 `satellite_result`는
  L289 `st.session_state.get("champion_satellite_result")`(= "🔍 빠른 근사 스캔" 탭,
  `compute_satellite_recommendation`)에서만 채워진다. 반대로 "✅ 백테스트와 동일한 방법" 탭의
  결과(`satellite_pit_result`, L238)는 diff 계산에 넘겨지지 않는다.
- **영향**: 오늘 실측으로 두 방법이 완전히 다른 종목(CAT/GEV/JNJ vs CRWD/TRV/BBY/META/T,
  겹침 0개)을 추천함이 확인됐다 — 페이지의 실제 매매 diff 표는 백테스트 성과와 무관한 조합을
  보여준다.
- **제안 스펙**: L555의 `satellite_result` 인자를 `st.session_state.get("champion_satellite_
  pit_result")`로 교체(또는 두 결과 중 point-in-time을 기본, naive를 옵션으로 만드는 selectbox
  추가). `compute_rebalance_diff()` 자체는 `selected`/`per_ticker_weights`/`unallocated_weight`
  키만 있으면 되므로 두 함수의 반환 형식과 이미 호환된다 — **`core/champion_strategy.py` 수정은
  필요 없고, `app/pages/11_챔피언_전략.py`의 변수 연결(약 1줄) 수정만 필요**. 사람이 확인 후
  반영 권장.

### 격차 #2 (중요도: 낮음, 운영상) — 격리 worktree에는 실제 포트폴리오 데이터가 없다

- **현상**: 이 R&D 에이전트 실행 환경(PROGRESS.md 작업67이 확립한 "Codespace 서브에이전트,
  격리 worktree" 아키텍처)은 매번 빈 로컬 DB에서 시작한다 — `init_db()`를 호출해도 테이블만
  생기고 사용자의 실제 보유/현금 데이터는 없다(그 데이터는 메인 체크아웃의 `data/quant.db`에만
  있고, `.gitignore`로 커밋되지 않으며 worktree 간에도 공유되지 않는다).
- **영향**: 이 에이전트가 매일 밤 실행돼도 "진짜 실행 가능한 매수/매도 수량"까지는 자동으로 못
  만든다 — 목표비중표까지만 만들고, 실제 diff는 사용자가 메인 환경에서 수동으로 대조하거나
  스크립트를 다시 돌려야 한다.
- **제안 스펙(코드 변경 아님, 운영 방식 논의 필요)**: 매일 밤 완전 자동 diff까지 원한다면
  (a) 이 E 에이전트를 격리 worktree가 아니라 메인 체크아웃에서 실행하거나, (b) 읽기 전용으로
  메인 `data/quant.db`를 worktree에 마운트/복사하는 방법이 있다 — 둘 다 "다른 세션과 충돌 없음"
  이라는 현재 격리 방식의 안전성과 트레이드오프가 있으므로 이 에이전트가 임의로 결정하지 않고
  사용자 판단이 필요하다.
