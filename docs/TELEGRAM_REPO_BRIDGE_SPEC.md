# 텔레그램 ↔ GitHub ↔ VM 연결 설계 (제안, 2026-09-24)

> 상태: **전부 구현·배포 완료 (2026-09-24)**. 사용자가 "전부 다"를 선택해 1~4단계를 모두 만들었다.
> 배경: 사용자가 "텔레그램-GitHub-VM 간 정보 이동, 무지성 커밋, 유연한 연결성"을 요청.
> 아래 1·2번은 그때의 현황 진단이라 그대로 두고(왜 만들었는지의 근거), 3번 각 항목에 구현 결과를 덧붙였다.

## 1. 지금 실제로 연결된 것 (2026-09-24 코드·VM 직접 확인)

| 방향 | 현재 상태 | 비용 / 지연 |
|---|---|---|
| 텔레그램 → VM | 명령(`/status` `/queue` `/diff` `/processes` …) + 자유 지시 | 명령은 즉시 / 자유 지시는 수 분 + Claude 할당량 |
| VM → 텔레그램 | 작업 결과, 배포 알림 6종, 매일 브리핑 HTML, 뉴스, 워치독, 백업 경고 | 즉시 |
| VM → GitHub | 에이전트가 작업 끝에 commit + push (`RESUME_NOTE.md`는 push 성공 후에만 삭제) | 작업당 |
| GitHub → VM | `quant-auto-deploy.timer` 5분 폴링 → 테스트 게이트 → 재시작 | ≤ 5분 |
| **텔레그램 → GitHub** | **없음** — LLM 작업을 띄우는 것 말고는 경로가 없다 | 수 분 + 할당량 |
| **GitHub → 텔레그램** | **거의 없음** — 자동배포가 커밋을 주워갈 때 간접적으로만 | — |
| **폰에서 저장소 읽기** | **없음** — 파일 한 줄 보려고 LLM 작업을 띄워야 한다 | 수 분 + 할당량 |
| **사진/파일 수신** | **없음** — 러너에 `photo`/`document` 처리가 0줄 | — |

`/idea`는 VM 로컬 SQLite `ideas` 테이블에만 저장되고 **GitHub에는 영영 안 올라간다** — "무지성 커밋"이 없다는 뜻이다.

## 2. 이 설계가 필요하다는 실제 증거

`Oracle capacity retry` 워크플로가 **최근 100회 연속 실패**(2026-09-09 ~ 09-24, 총 누적 1,023회 실행)하고 있었는데
아무도 몰랐다. VM은 이미 확보됐으니 이 워크플로의 목적 자체가 끝났고, `vars.ORACLE_VM_READY`가 `true`가 아니라
계속 실행을 시도하다 죽는 중이다(OCI 키가 401이라 성공할 수도 없다 — 같은 키가 이 Codespace에서도 401).

즉 **GitHub에서 벌어지는 일은 폰으로 전달되는 경로가 없어서 15일간 조용히 실패**했다. 이게 3번 항목의 근거다.

## 3. 제안: 빠진 세 조각

### 3-1. `/note`, `/progress` — 무지성 커밋 (LLM 0, 수 초)

텍스트·사진·파일을 텔레그램에 던지면 저장소에 커밋·푸시한다. Claude를 전혀 안 부른다.

**어느 저장소로 갈지가 핵심 결정이다. Quant 저장소는 공개다.** 폰에서 급하게 친 메모에 뭐가 들어갈지 모른다.

| 명령 | 목적지 | 왜 |
|---|---|---|
| `/note <텍스트>` 또는 사진/파일 | **비공개** `quant-vm-backup` 저장소의 `notes/2026-09/24.md` | 개인 메모·스크린샷의 안전한 기본값. 이미 있는 저장소라 새로 만들 게 없다 |
| `/progress <텍스트>` | **공개** Quant 저장소의 `PROGRESS.md` 끝에 append | 프로젝트 기록은 원래 공개였고, `progress_reconcile.sh`가 이미 이 파일의 동시 수정을 union 병합으로 안전하게 처리한다 |

안전장치:
- 커밋 전에 `backup_vm.py`의 비밀 패턴 검사(`SECRET_NAME_RE` / `SECRET_CONTENT_RES`)를 그대로 재사용 — 키·토큰처럼 보이면 **커밋을 거부**하고 그 사실만 알린다(내용은 출력하지 않음).
- 건드릴 수 있는 경로는 `notes/`와 `PROGRESS.md` 뿐. 코드에는 손댈 수 없다.
- push 충돌 시 `pull --rebase` 후 1회 재시도, 그래도 실패하면 VM에 보존하고 텔레그램으로 알린다(내용 유실 없음).
- 공개 저장소로 가는 `/progress`는 첫 사용 때 "이건 공개 저장소입니다" 한 줄을 응답에 붙인다.

### 3-2. `/cat`, `/log`, `/repo` — 폰에서 저장소 읽기 (LLM 0, 즉시)

- `/cat PROGRESS.md 30` → 그 파일 마지막 30줄 (길이 상한 있음, 바이너리 거부)
- `/log 5` → 최근 커밋 5개 한 줄 요약
- `/repo` → VM의 git 상태: HEAD, origin과의 차이, 미커밋 파일 목록

지금은 "PROGRESS 마지막 항목 뭐였지?"를 확인하려고 수 분짜리 LLM 작업을 띄워야 한다.

### 3-3. GitHub 이벤트 → 텔레그램 (시크릿 불필요)

Quant 저장소가 **공개**라서 VM이 **토큰 없이** GitHub API로 Actions 결과를 읽을 수 있다(오늘 VM에서 직접 확인).
따라서 저장소 시크릿을 등록할 필요가 없다 — 사람이 할 설정이 0이다.

- 워치독(또는 전용 타이머)이 15분마다 `GET /repos/sternjeong/Quant/actions/runs`를 읽는다.
- 마지막으로 알린 run id를 상태 파일에 저장해 **새로 실패한 것만** 한 번씩 알린다(같은 실패 반복 알림 없음).
- 비인증 한도는 시간당 60회 — 15분 간격이면 시간당 4회라 충분하다.

이러면 `uptime.yml`(30분마다 공개 주소·인증서·닫힌 포트 점검) 결과도 폰까지 도달한다.

## 4. 함께 정리할 것 (독립적으로도 해야 하는 일)

- `Oracle capacity retry` 워크플로를 **끈다**. VM을 이미 확보해서 목적이 끝났고, 15일째 실패만 쌓고 있다.
  (워크플로 파일에서 `schedule:`을 빼거나 저장소 변수 `ORACLE_VM_READY=true`를 설정하면 `if:` 조건으로 건너뛴다.)

## 5. 만들지 않기로 한 것과 이유

- **GitHub 웹훅 수신**: VM에 공개 엔드포인트를 하나 더 여는 셈이라(nginx 경로 + 서명 검증) 폴링 대비 이득이 적다. 15분 지연이면 충분하다.
- **저장소 시크릿에 텔레그램 토큰 등록**: 공개 저장소라 포크 PR 관련 주의가 필요한데, 3-3이 비인증 폴링으로 같은 결과를 내므로 불필요하다.
- **아무 경로나 쓰는 범용 `/write` 명령**: 폰에서 오타 하나로 코드가 깨질 수 있다. 경로를 `notes/`와 `PROGRESS.md`로 묶는 편이 안전하다.

## 6. 구현 결과 (2026-09-24)

| 단계 | 결과 | 위치 |
|---|---|---|
| 1. `Oracle capacity retry` 끄기 | 완료 — `schedule:` 제거(수동 실행은 남김) | `.github/workflows/oracle_capacity_retry.yml` |
| 2. 읽기 명령 `/cat` `/log` `/repo` | 완료 — 경로 탈출·바이너리·길이 방어 + 기존 `redact()` 통과 | `deploy/codex_telegram/runner.py` |
| 3. GitHub 감시 | 완료 — 15분 타이머, **토큰 불필요**, 첫 실행은 기준선만 | `deploy/github_watch.py`, `quant-github-watch.{service,timer}` |
| 4. `/note` `/progress` + 사진·파일 | 완료 — 아래 설계 그대로 | `deploy/codex_telegram/runner.py` |

구현하면서 설계에서 바뀐 점(더 안전한 쪽으로):

- **`/note`의 목적지**: 비공개 저장소에 *직접* 쓰지 않는다. `/opt/quant/notes/`(공개 저장소에선 `.gitignore`로 차단)에
  저장하고, 이미 검증된 **야간 백업**(`deploy/backup_vm.py`의 `ALLOWED_PREFIXES`에 `notes/` 추가)이 비공개 저장소로
  가져간다. 새 자격증명·새 저장소가 필요 없고, 백업의 비밀 스캔·검증·복구 리허설을 그대로 물려받는다.
  대신 GitHub 도달은 **다음 백업(매일 06:30 KST)까지 지연**된다 — 그 사이엔 VM 디스크에만 있다.
- **`/progress`의 커밋 방식**: 워킹트리를 아예 쓰지 않고 git 배관(`hash-object` → 임시 인덱스에 `read-tree`/
  `update-index` → `write-tree` → `commit-tree` → `push`)으로 `origin/main` 위에 커밋을 만든다. VM 워킹트리에는
  리서치 에이전트의 미커밋 수정이 상시 있어서 `checkout`/`rebase`/`pull` 류는 위험하기 때문이다. origin이 그 사이
  움직이면 한 번 다시 만든다. 테스트가 "더러운 워킹트리가 바이트 단위로 그대로인지"를 검증한다.
- **사진·파일**: 예전에는 텍스트 없는 메시지가 통째로 버려졌다(`ingest()`가 `text`만 봤다). 이제 사진·문서를 받으면
  `notes/attachments/`에 저장하고 캡션을 그날 메모에 남긴다. 20MB 상한(텔레그램 봇 다운로드 한도).

테스트: `deploy/codex_telegram/test_runner.py` 62개(읽기 명령 9개 + 무지성 커밋 14개 포함), `tests/test_github_watch.py` 12개.
