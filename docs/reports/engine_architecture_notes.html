Module ①

신호 생성 엔진 core/strategy_engine.py

"RSI가 30 밑이면" 같은 조건을 실제 불리언 시계열로 바꾸는 곳입니다. 지표가 늘어나도 이 엔진의 나머지 로직은 손대지 않도록 레지스트리 패턴으로 짜여 있습니다.

패턴 · 레지스트리

지표 이름 → 평가 함수 딕셔너리

# INDICATOR_EVALUATORS: dict[str, Callable] INDICATOR_EVALUATORS = { "ma_cross": _eval_ma_cross, "rsi": _eval_rsi, "bollinger": _eval_bollinger, # ... 28개 지표(캔들패턴 포함)가 같은 시그니처로 등록됨 } def evaluate_condition(df, condition): evaluator = INDICATOR_EVALUATORS[condition["indicator"]] return evaluator(df, condition) # bool Series 반환

새 지표를 추가할 때 combine_conditions()나 extract_trades() 같은 나머지 엔진 코드는 전혀 건드릴 필요가 없습니다 — core/indicators.py에 계산 함수를 만들고 이 딕셔너리에 한 줄만 등록하면 AND/OR 조합, 차트 오버레이, 백테스트까지 자동으로 연결됩니다.

같은 파일에 INDICATOR_CATEGORIES(지표 이름 → "추세"/"모멘텀"/ "변동성"/"거래량"/"캔들패턴"/"반전패턴")라는 자매 딕셔너리도 있습니다 — 계산 로직과는 무관하고 순전히 UI가 "이 전략은 어떤 유형의 지표로 구성됐는지"를 캡션으로 보여주거나 (categorize_indicators()), 앙상블 지표 선택기에서 카테고리별로 묶어 보여주는 데만 쓰입니다.

패턴 · 6개 스키마 통일

evaluate_boolean_signal() — 공용 진입점

이 저장소는 전략을 여섯 가지 방식(레짐 AND/OR, 직접 수식, 1:2:6 단계별, 전략 합성, 코스톨라니 국면, 앙상블 스코어링)으로 저장할 수 있습니다. 서로 다른 JSON 구조를 판별해서 전부 "지금 포지션을 들고 있는가"라는 하나의 불리언 시계열로 통일하는 게 이 함수의 역할입니다.

def evaluate_boolean_signal(df, config): if is_kostolany_config(config): # {"schema": "kostolany", ...} return generate_kostolany_position(df, config) > 0 if is_ensemble_config(config): # {"schema": "ensemble", ...} return generate_ensemble_position(df, config) > 0 if is_combined_config(config): # {"combine": "AND", "strategies": [...]} return AND/OR 로 하위 전략들을 재귀 결합 if is_staged_config(config): # {"entry_stages": [...]} return simulate_staged_positions(df, config)[0] > 0 return generate_regime_signal(df, config) # 레짐 AND/OR 또는 직접 수식

복합 전략(전략 합성)은 하위 전략이 다시 복합 전략일 수도 있어 재귀로 처리됩니다 — "A AND (B OR C)" 같은 임의 깊이의 조합이 가능한 이유입니다.

신규 · 여섯 번째 스키마

compute_ensemble_score() — 이진 판정 대신 연속 점수

나머지 다섯 스키마는 결국 불리언(참/거짓) 조건을 조합합니다. 앙상블은 다릅니다 — 지표별 "원값"(예: RSI 값, MACD 히스토그램)을 롤링 z-점수 + tanh로 -1~1 범위로 표준화한 뒤 가중평균합니다.

# SCORE_EVALUATORS: 원값(raw)을 반환하는 레지스트리 — INDICATOR_EVALUATORS(bool 반환)와 대칭 SCORE_EVALUATORS = { "rsi": lambda df, c: compute_rsi(df, period=c["period"]), "macd_hist": lambda df, c: compute_macd(df, ...)["hist"], "ma_spread": _ma_spread, # (단기이평-장기이평)/장기이평 — 추세 강도/방향의 연속값 # ... percent_b, mfi, roc } def compute_ensemble_score(df, config): weighted_sum = 0 for cond in config["indicators"]: raw = SCORE_EVALUATORS[cond["indicator"]](df, cond) score = _zscore_tanh(raw, window=config.get("zscore_window", 60)) if cond.get("mode") == "mean_revert": score = -score # 과매수=악재, 과매도=호재로 해석 반전 weighted_sum += score * cond.get("weight", 1.0) return (weighted_sum / 총_가중치).clip(-1, 1)

이후 generate_ensemble_position()이 이 점수에 진입/청산 임계값(히스테리시스)을 적용해 0~1 비중으로 바꾸고, extract_weighted_trades()가 그 연속 비중에서 매매(Trade) 목록을 추출합니다(0/1 이진 포지션의 extract_trades()와 같은 "진입~청산 사이클" 로직을 연속값에 맞게 재구현한 버전).

기존 엔진과 어떻게 맞물리는가. core.backtest_engine._simulate_on_raw()가 is_ensemble_config()를 확인해 이 경로로 분기하는 것 말고는, 앙상블 전략도 compute_equity_curve()·calculate_metrics()· Masters 4대 검증·전략 상관관계까지 나머지 파이프라인을 전부 그대로 통과합니다 — 6번째 스키마를 추가하면서 기존 백테스트 엔진 코드는 한 줄도 안 바뀌었습니다(스키마별 포지션 생성 로직만 갈아끼우는 설계 덕분).

구현 core/strategy_engine.py · SCORE_EVALUATORS, _zscore_tanh(), compute_ensemble_score()
패턴 · 상태 머신

1:2:6 단계별 진입 — simulate_staged_positions()

후지모토 시게루류 분할매매를 흉내 냅니다. 하루하루 반복문을 돌며 "지금 몇 단계까지 진입했는지"(stage_level)와 "각 단계별로 얼마나 물려있는지" (open_tags: dict[단계, 비중])를 갱신하는 상태 머신입니다.

# 매 거래일 i 마다: for k in range(1, n_entry+1): if entry_signals[k][i] and (이전 단계까지 진입된 상태 or 마지막 단계): open_tags[k] = entry_weights[k] # k단계 진입 if emergency_signal[i]: open_tags = {} # 긴급청산 최우선 elif 종가 >= 목표익절가: open_tags = {} # 손절 대비 N배 익절 elif 종가 < 손절레벨: open_tags = {} # 진입 시점에 고정된 레벨 elif 마지막 청산단계 신호: open_tags = {} # 잔량 전부 정리 else: 개별 단계만 부분 청산 weight_signal[i] = sum(open_tags.values())

왜 이렇게 짰는가. 손절/익절 레벨은 진입 사이클이 시작되는 그 순간 한 번 스냅샷해서 고정합니다 — 이후 지표가 다시 움직여도 그 사이클이 끝날 때까지는 처음 정한 레벨을 그대로 씁니다. 그래야 "손절선이 매일 지표 따라 흔들리는" 비현실적인 시뮬레이션을 피할 수 있습니다.

패턴 · 룩어헤드 방지

extract_trades() — 다음날 체결

executed_position = position.shift(1).fillna(0) # 신호는 오늘, 체결은 내일 for i in range(len(df)): if executed_position[i] == 1 and executed_position[i-1] == 0: entry_idx = i # 진입 체결일 elif executed_position[i] == 0 and executed_position[i-1] == 1: Trade(entry_idx, i, ...) # 청산 체결일 -> 매매 1건 완성

신호가 발생한 날의 종가는 "이미 그날 장이 끝난 뒤"에나 확정되므로, 그 신호로 실제 주문을 넣을 수 있는 가장 빠른 시점은 다음 거래일입니다. 이 한 줄(shift(1))이 이 엔진 전체의 룩어헤드 편향 방지 원칙입니다.

Module ②

백테스팅 엔진 core/backtest_engine.py

포지션 시계열을 받아 자산가치 곡선을 만들고, 그 곡선이 통계적으로 신뢰할 만한지 네 가지 방법으로 검증합니다. 저장소에서 가장 크고 중심적인 모듈입니다.

핵심 · 복리 계산

compute_equity_curve() — 자산가치 곡선

daily_return = 종가.pct_change() executed_position = position.shift(1) # 룩어헤드 방지 turnover = |executed_position[t] − executed_position[t-1]| cost = turnover × (fee_bps + slippage_bps) / 10000 strategy_return[t] = daily_return[t] × executed_position[t] − cost[t] equity = (1 + strategy_return).cumprod() × 100 # 시작=100

포지션이 0/1이든, 1:2:6 전략의 0~1 비중이든 같은 공식이 그대로 통합니다 — 비중이 부분적으로만 바뀌면(예: 0.1→0.3) 회전율도 그만큼만(0.2) 잡혀 비용도 비례해서만 발생합니다.

함수compute_equity_curve(), simulate_contribution_equity()(월 적립 버전)
핵심 · 지표 파이프라인

calculate_metrics() — 9개 지표를 한 번에

자산가치 곡선과 매매 리스트(list[Trade]) 두 가지만 입력받아 누적수익률·CAGR·MDD·샤프·승률·매매횟수·손익비·칼마지수·평균낙폭지속기간을 전부 계산해 하나의 dict로 반환합니다. 아래는 그중 두 지표가 "정의되지 않는 경우"를 처리하는 방식입니다.

상황처리
진 거래가 0건 (손익비 분모=0)_RATIO_METRIC_CAP = 999.0으로 캡핑
낙폭이 0 (칼마지수 분모=0)CAGR>0이면 999.0, 아니면 0.0
매매 0건 / 자산곡선 2일 미만모든 지표 0으로 채운 dict를 조기 반환

왜 inf 대신 999.0인가. 수학적으로는 무한대가 맞지만, SQLite Float 컬럼·JSON 직렬화·Streamlit 데이터프레임 전 구간에서 inf를 안전하게 다루려면 번거로운 예외 처리가 곳곳에 필요합니다. "사실상 무한대"를 뜻하는 유한한 상한값 하나로 그 복잡도를 없앴습니다.

신규 · 전략 수명

compute_alpha_decay() — 재튜닝 없이 재적용

full_run = run_backtest(ticker, config, full_start, full_end) recent_run = run_backtest(ticker, config, today−N개월, today) # 같은 config! decay_ratio = recent_run.sharpe / full_run.sharpe is_decayed = decay_ratio < 0.3 or recent_run.sharpe < 0

신규 · 홀리그레일

compute_strategy_correlation() — 종목이 아닌 전략끼리

core.portfolio의 상관관계는 "종목" 간 계산이지만, 이 함수는 동일한 계산을 "전략"의 자산가치 곡선에 적용합니다. 여러 전략을 run_strategy_portfolio()로 한 번에 백테스트한 뒤, 각 곡선의 일간수익률을 뽑아 상관계수 행렬을 만듭니다.

returns = {label: run.equity_curve.pct_change() for label, run in runs.items()} corr_matrix = DataFrame(returns).corr() # 국면별 버전 — 순환참조 방지를 위해 함수 안에서 지연 import from core import market_regime regime_corr = market_regime.compute_regime_conditional_correlation(returns_df)

순환참조를 피하는 법. market_regime.py는 DEFAULT_BENCHMARK_TICKER 상수를 쓰려고 모듈 최상단에서 backtest_engine을 import합니다. 그래서 반대 방향 (backtest_engine → market_regime)은 함수 안에서 지연 import해야 순환 임포트 에러가 나지 않습니다 — 이 저장소 전체에서 반복되는 규칙입니다.

신규 · 이력 누적

save_strategy_correlation_snapshot() — 한 번이 아니라 계속 쌓기

"이번 달 상관관계가 높다고 바로 판단하지 말라"는 원칙을 지키려면 상관관계도 한 번 계산하고 끝내는 게 아니라 이력을 쌓아야 합니다. CorrelationSnapshot 테이블 하나를 kind="strategy"(core.backtest_engine)와 kind="portfolio"(core.portfolio) 양쪽이 공유합니다 — 저장 시점의 평균/최댓값(비대각 원소 기준)을 함께 남겨, 매번 전체 행렬을 다시 열지 않고도 추이만 빠르게 훑어볼 수 있게 했습니다.

off_diag = corr_matrix.to_numpy()[~np.eye(n, dtype=bool)] # 대각선(자기 자신=1) 제외 CorrelationSnapshot(kind="strategy", avg_correlation=off_diag.mean(), max_correlation=off_diag.max(), ...)

왜 새 테이블을 또 안 만들었는가. StrategyDecayCheck와 똑같은 "스냅샷 누적" 문제라 똑같은 해법을 재사용했습니다 — 다른 점은 "무엇을 kind로 구분해 한 테이블에 같이 담을지"뿐입니다. 모듈 ⑤의 스냅샷 캐싱 패턴과는 결이 달라 보이지만(그쪽은 "최신 1개만 빠르게 읽기", 이쪽은 "이력 전체를 훑어 추이 보기") 저장 방식 자체는 동일합니다.

설계 원칙 · 순수 함수

왜 이 모듈만 이렇게 얇은가

fixed_fractional_size(), kelly_fraction(), volatility_target_weight() 넷 다 숫자를 받아 숫자를 반환하는 순수 함수입니다. 백테스트 엔진의 Trade 리스트나 실시간 시세를 "어디서 가져올지"는 전혀 모르고, 호출부(Streamlit 페이지, core.portfolio)가 그 값을 만들어 넘겨줍니다.

# 전략 스튜디오가 이 모듈을 쓰는 방식 (app/pages/1_전략_스튜디오.py) trade_stats = position_sizing.compute_trade_stats(strategy_run.trades) # 백테스트 결과에서 kelly = position_sizing.kelly_fraction(trade_stats.win_rate, ...) # 계산만

이렇게 짜면 뭐가 좋은가. 이 4개 함수는 계좌 크기가 얼마든, 크립토든 주식이든, 심지어 이 저장소 밖 다른 프로젝트에서도 그대로 재사용할 수 있습니다 — 순수 함수라 어떤 문맥에 갖다 놔도 항상 같은 입력에 같은 출력을 냅니다.

Module ④

포트폴리오 관리 core/portfolio.py

실제 보유 종목의 손익·리스크를 계산합니다. "계산 함수"와 "조회+계산을 합친 함수"를 의도적으로 분리한 게 이 모듈의 핵심 설계입니다.

설계 원칙 · compute_* vs get_*

두 계층으로 나뉜 함수 이름

계층예시특징
compute_*compute_correlation_matrix(), compute_portfolio_volatility()순수 함수, 단위 테스트 쉬움
get_*get_portfolio_risk(), get_recommended_weights()DB/시세 조회 + compute_* 조합, 실사용 진입점

get_portfolio_risk()가 한 번 조회한 daily_returns를 결과 dict에 그대로 담아 반환하기 때문에, get_recommended_weights()와 get_regime_conditional_correlation()은 시세를 다시 조회하지 않고 그 값을 재사용합니다.

risk = get_portfolio_risk(pnl_df) # 시세 조회 1회 weights = get_recommended_weights(risk) # risk["daily_returns"] 재사용, 조회 없음 regime_corr = get_regime_conditional_correlation(risk) # 마찬가지

왜 이렇게 짰는가. 종목 시세 조회는 이 앱에서 가장 느린 작업입니다. 같은 화면에 리스크·추천비중·국면별상관관계 세 섹션을 보여주면서 시세를 세 번 따로 조회하면 페이지가 세 배 느려집니다.

Module ⑤

시장 국면 분류기 core/market_regime.py

"지금 강세장인가 약세장인가"를 규칙 기반으로 판정합니다. 머신러닝이 아니라 우선순위가 명확한 규칙의 나열이라, 왜 그 날이 그 국면으로 라벨링됐는지 항상 설명할 수 있습니다.

핵심 · 규칙 우선순위

classify_daily_regime() — 3단 캐스케이드

if 52주_고점_대비_낙폭 <= −20%: 국면 = "약세장" # ① 최우선 — 공식적인 약세장 정의 elif ADX(14) < 20: 국면 = "횡보장" # ② 추세 자체가 약함 else: 국면 = "강세장" if 종가 > SMA200 else "약세장" # ③ 200일선 기준

모든 날이 반드시 셋 중 하나로 라벨링되고(판단 근거가 부족한 초반 구간은 "횡보장"으로 기본 처리), 벡터 연산만으로 계산되기 때문에 5년치 이력을 매일 밤 훑는 워크포워드 튜닝에서도 충분히 빠릅니다.

패턴 · 스냅샷 캐싱

무거운 계산은 밤에 미리, 낮에는 읽기만

S&P500 전 종목을 훑는 get_market_regime_snapshot()은 페이지를 열 때마다 돌리기엔 무겁습니다. 그래서 스케줄러가 매일 한국시간 00:00에 한 번 계산해 MarketRegimeSnapshot 테이블에 저장하고, 페이지는 가장 최근 행을 읽기만 합니다 — 덮어쓰지 않고 계속 쌓아서 국면 변화 추이도 나중에 볼 수 있습니다.

이 저장소 상시 서버가 없는 배포 환경(Streamlit Community Cloud)에서는 GitHub Actions가 같은 결과를 JSON으로 커밋해두는 폴백까지 있습니다 — get_latest_market_regime_snapshot()이 DB와 그 JSON 중 더 최신인 쪽을 골라 반환합니다.

같은 패턴이 재사용되는 곳. SectorStrengthSnapshot, KostolanyCycleSnapshot, 그리고 이번에 추가한 StrategyDecayCheck까지 — "계산은 무겁고 자주 안 바뀌는데 자주 보여줘야 한다"는 문제를 이 저장소는 전부 같은 스냅샷-이력 패턴으로 푼다.

Cross-cutting

모듈을 가로지르는 공통 설계 패턴

개별 모듈보다, 이 네 가지 패턴을 이해하면 저장소 전체를 훨씬 빨리 읽을 수 있습니다.

Pattern 01

백그라운드 작업 실행기

core/job_manager.py — Streamlit은 페이지를 이동하면 실행 중이던 스크립트를 끊어버립니다. 무거운 백테스트는 별도 스레드풀에서 돌리고 페이지는 폴링만 하도록 분리해, 사용자가 다른 페이지로 이동해도 계산이 계속됩니다.

Pattern 02

스키마 마이그레이션

core/db.py의 _add_missing_columns() — SQLAlchemy의 create_all()은 없는 테이블만 만들 뿐 기존 테이블에 나중에 추가된 컬럼은 못 채웁니다. 그래서 ALTER TABLE ADD COLUMN을 직접 실행하는 최소 마이그레이션 함수를 둡니다 (이번 세션의 profit_factor, calmar, avg_drawdown_days 컬럼도 이 방식으로 추가됨).

Pattern 03

지연 import로 순환참조 차단

backtest_engine ↔ market_regime처럼 서로를 참조해야 하는 모듈 쌍은, 한쪽은 모듈 최상단에서 import하고 반대쪽은 함수 안에서 그때그때 import합니다. 새 모듈을 추가할 때 이 방향을 지키지 않으면 앱 시작부터 ImportError가 납니다.

Pattern 04

선택적 비용 파라미터

fee_bps=0.0, slippage_bps=0.0 같은 새 파라미터는 항상 기본값을 "이전과 동일한 동작"으로 둡니다. 그래야 core/kostolany_scenario_engine.py처럼 이미 있던 20곳 넘는 호출부를 하나도 안 고쳐도 됩니다 — 이번 세션에서 비용 모델링을 추가할 때 실제로 적용한 원칙입니다.

Guide

처음 읽는다면 이 순서로

  1. core/strategy_engine.py의 evaluate_boolean_signal()부터 — 전략이 결국 "0/1 시계열"로 귀결된다는 걸 이해하면 나머지가 다 쉬워집니다.
  2. core/backtest_engine.py의 compute_equity_curve()와 calculate_metrics() — 딱 이 두 함수가 저장소 전체의 심장입니다.
  3. tests/test_backtest_engine.py를 나란히 열어두고 — 각 함수가 어떤 입력·출력을 기대하는지 테스트 케이스만큼 빠르게 알려주는 문서는 없습니다.
  4. 그다음 core/position_sizing.py → core/portfolio.py → core/market_regime.py 순서로 — 전부 앞의 두 모듈이 만든 결과(Trade 리스트, 자산가치 곡선)를 "받아서" 쓰는 소비자입니다.
